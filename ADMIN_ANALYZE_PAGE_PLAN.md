# План: страница анализа книги в админке

Дата: 2026-09-14. Статус: все этапы 0–5 выполнены (2026-09-14 … 2026-09-18). Остался ручной прогон в браузере по чеклисту раздела 6.

## 1. Цель

Страница `/admin/analyze`, на которой администратор:

1. указывает PDF книги (из уже загруженных в `lib/analyzer/books/` или загружает новый), название и серию (`BookSeriesId`, необязательно);
2. после выбора PDF автоматически попадает на шаг 2: видит оценку объёма книги в токенах и выбирает размер фрагмента (по умолчанию 100 000 токенов) и LLM (по умолчанию `deepseek-v4.1-flash`);
3. нажимает «Запустить» и получает тот же результат, что команда
   `pnpm analyze "<pdf>" -m deepseek-v4.1-flash --chunk-tokens 100000 -o lib/analyzer/generated/<...>.analysis.json`;
4. видит на странице в реальном времени все строки, которые анализатор пишет через `log()` из `lib/analyzer/llm-client.ts`, плюс сообщения о фазах из `analyzer.ts` и `executor.ts`;
5. после завершения может открыть JSON и опубликовать книгу в БД с выбранной серией.

## 3. Ключевые архитектурные решения

### 3.1. Анализ выполняется как фоновая задача в процессе Next, а не внутри HTTP-запроса

Сейчас `GET /api/admin/analyze` держит стрим открытым на всё время анализа. Это значит: перезагрузил страницу или уснул ноутбук, и прогресс потерян из виду. Вместо этого:

- `POST /api/admin/analyze/jobs` создаёт задачу и сразу возвращает `jobId`;
- задача выполняется в процессе сервера, все логи копятся в памяти;
- `GET /api/admin/analyze/jobs/[id]/events` отдаёт SSE: сначала повтор всех накопленных строк, потом живые;
- `jobId` кладётся в URL (`/admin/analyze?job=...`), так что перезагрузка страницы просто переподключается.

Реестр задач хранится на `globalThis` по тому же принципу, что `prisma` в `lib/db.ts`, иначе HMR в dev сбросит его при первой правке файла.

Ограничение, которое нужно принять явно: это работает на локальной машине и на self-hosted сервере с долгоживущим процессом. На Vercel serverless-функция умрёт по таймауту раньше, чем закончится первый фрагмент. Страница предназначена для локального запуска админом, как и CLI.

### 3.2. Логи собираются через AsyncLocalStorage, а не через подмену `console.log`

Сейчас `log()` пишет в консоль, а `analyzer.ts` и `executor.ts` местами пишут `console.log` напрямую и рисуют спиннеры `ora`. Нужен единый канал:

- `lib/analyzer/run-context.ts`: `AsyncLocalStorage<RunContext>`, где `RunContext = { emit(line: LogLine): void; signal: AbortSignal }`;
- `log()` в `llm-client.ts` берёт контекст из хранилища: если он есть, вызывает `emit`, иначе пишет в консоль как сейчас;
- `analyzer.ts` и `executor.ts` переводятся с `console.log`/`ora` на функции `log()` и `phase()` из того же модуля; `ora` остаётся только когда контекста нет и `process.stdout.isTTY`;
- глобальный `abortController` в `llm-client.ts` заменяется на `signal` из контекста, чтобы кнопка «Отменить» останавливала конкретную задачу, а не все запросы процесса.

Так один и тот же код анализатора даёт одинаковый вывод в терминале и на странице, и параллельные задачи не перемешивают логи.

### 3.3. Общий раннер для CLI и API

Логика «проверить готовый JSON, извлечь текст, посчитать путь вывода, запустить `analyzeBook`, записать файл, показать usage» сейчас продублирована в `lib/analyzer/index.ts` и в API-маршруте с расхождениями (маршрут не умеет `chunkTokens`, `fresh`, `batch`, кладёт файл по другому пути). Выносим в `lib/analyzer/run.ts`:

```ts
runAnalysis({ pdfPath, model, chunkTokens?, title?, fresh?, batch?, outputPath? })
  -> { outputPath, result, usage, elapsedMs }
estimateBook(pdfPath) -> { pages, chars, estimatedTokens, language, chunkCounts: Record<number, number> }
```

CLI-команда `analyze` и API вызывают одно и то же. Путь вывода по единому правилу: `lib/analyzer/generated/<model-slug>/<basename>.c<chunkK>k.analysis.json`.

### 3.4. Обработчик SIGINT переезжает из `llm-client.ts` в CLI

`llm-client.ts` при импорте вешает `process.once("SIGINT", ...)` с `process.exit(130)`. Внутри Next-сервера это перехватывает Ctrl+C у dev-сервера. Регистрация переносится в `lib/analyzer/index.ts`, где ей место.

### Этап 1. Реестр фоновых задач ✅ выполнен

Сделано: `lib/analyzer/jobs.ts` с очередью в одну задачу, кольцевым буфером событий, повтором по `seq` для `Last-Event-ID`, отменой через сигнал контекста и хранением на `globalThis`; 6 тестов в `lib/analyzer/__tests__/jobs.test.ts`. Отличие от плана: события пронумерованы единым `seq` (логи и статусы вместе), поэтому клиенту достаточно одного номера для повтора; `getEvents` сообщает `truncated`, если запрошенный хвост уже вытеснен.

Файл: `lib/analyzer/jobs.ts` (новый).

```ts
type JobStatus = "queued" | "running" | "done" | "error" | "cancelled";
interface AnalyzeJob {
  id: string;                 // crypto.randomUUID()
  params: { pdfPath; model; chunkTokens; title?; bookSeriesId?; fresh };
  status: JobStatus;
  createdAt; startedAt?; finishedAt?;
  logs: LogLine[];            // кольцевой буфер, максимум 5000 строк
  result?: { outputPath; title; characters: { main; secondary; minor }; events; usage };
  error?: string;
  abort: AbortController;
  subscribers: Set<(event: JobEvent) => void>;
}
```

Функции: `createJob(params)`, `getJob(id)`, `listJobs()`, `cancelJob(id)`, `subscribe(id, cb)`.
Запуск: `createJob` вызывает `runAnalysis` внутри `runWithContext({ emit: line => pushLog(job, line), signal })` без `await`, ошибки ловит и переводит статус в `error`.
Ограничение: одна задача в статусе `running` одновременно, остальные ждут в `queued`. Облачная модель и так параллелит описания, а два анализа сразу упрутся в лимиты Ollama.
Хранение: `globalThis.__analyzerJobs`, завершённые задачи держим последние 20.

Критерий готовности: юнит-тест на кольцевой буфер, отмену и повтор логов новому подписчику.

## 5. Безопасность

- Все маршруты только для `role === "admin"` через `requireAdmin`; layout уже редиректит остальных.
- Путь к PDF принимается только как имя файла внутри `lib/analyzer/books/`, без `..` и абсолютных путей; сервер сам собирает абсолютный путь.
- Имя модели валидируется регуляркой `^[a-z0-9._:/-]+$` длиной до 64 символов, чтобы не попасть в путь вывода чем-то лишним; slug для каталога считается так же, как в CLI.
- `chunkTokens` ограничить диапазоном 5 000–1 000 000.
- SSE и статус задач отдают только логи анализатора; ключи и переменные окружения в логи не попадают, `describeNetworkError` печатает хост, но не заголовки.

## 6. Проверка и приёмка

Автоматически:

- юнит-тесты `run-context` (захват логов, изоляция параллельных контекстов, сигнал отмены) и `jobs` (буфер, повтор, отмена, лимит одновременных задач);
- `tsc --noEmit` и `eslint` чисто, `next build` проходит с `cacheComponents`.

Вручную на `(Witcher 1)The Last Wish.pdf`:

1. Шаг 1 → выбор PDF → автоматический переход на шаг 2, оценка около 173 тыс. токенов, при 100 000 показано 2 фрагмента.
2. Запуск с `deepseek-v4.1-flash`: на странице появляются те же строки, что в терминале, включая «Промпт: ~… токенов» и «Ответ получен за …».
3. Перезагрузка страницы во время анализа: лог восстанавливается целиком, живые строки продолжают приходить.
4. Отмена: задача переходит в `cancelled`, следующий запуск с теми же параметрами берёт готовые фрагменты из `.work`.
5. Повторный запуск без `fresh` при существующем JSON: мгновенный `done` с предупреждением.
6. Публикация с серией в режиме dry-run: ответ с числом персонажей, в БД ничего не появилось; затем реальная публикация.
7. CLI `pnpm analyze` даёт тот же файл, что страница, при одинаковых параметрах.

## 7. Риски и открытые вопросы

- **Долгие задачи в процессе Next.** В dev-режиме перезапуск сервера убивает задачу; кэш `.work` смягчает потерю. Для продакшена на Vercel страница не подходит, нужно либо self-hosting, либо отдельный воркер. Решение отложено, фиксируем ограничение в README.
- **HMR и состояние в памяти.** Реестр на `globalThis`; при правке `jobs.ts` во время работающей задачи её лог всё равно может потеряться. Приемлемо для админ-инструмента.
- **Память под логи.** 5 000 строк на задачу и 20 задач в истории, порядка нескольких мегабайт. Достаточно.
- **Список моделей.** Статический, потому что каталог ollama.com не даёт лимитов и цен. Обновляется руками в `models.ts`.
- **Оценка токенов.** Считается по символам, а не токенизатором; для точного числа у Claude есть `count_tokens`, для Ollama точного способа без запроса нет. На шаге 2 это подписано.
